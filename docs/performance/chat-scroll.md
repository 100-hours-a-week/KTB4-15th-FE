# 채팅 런타임 성능 개선 요약

관련: [PR #230](https://github.com/100-hours-a-week/KTB4-15th-FE/pull/230), [이슈 #218](https://github.com/100-hours-a-week/KTB4-15th-FE/issues/218). 측정일: 2026-11-08~09.

날짜 포맷터 재사용, 기존 메시지 memo, 메시지 가상화를 적용했습니다. 이전 내역 추가 시 읽던 위치와 상품 선택 상태를 유지합니다.

## 측정 조건

- 일반 프로덕션 빌드, headless Chromium 156.0.8078.4, 390×844, DPR 1, CPU 4배 감속.
- 고정 USER·AI 교대 메시지, AI 답변마다 상품 2개·상품당 로컬 이미지 1개. 실제 서버·운영 이미지는 제외했습니다.
- 포맷터·memo: 최근 20개부터 20개씩 49회 추가해 총 1,000개. 응답 지연 200ms. 페이지마다 아래 400px 후 위 8,000px를 12,000px/s로 입력. 예행 1회 뒤 각 5회.
- 가상화: 2,000개를 미리 로드하고 추가 조회 없이 36,000px를 12,000px/s로 하향 스크롤. 예행 1회 뒤 각 3회.
- 20,000개 검증: PR head `a82a7a9`에서 같은 스크롤 입력과 CPU 조건으로 예행 1회 뒤 각 5회. 이전 20개 추가는 저장 20,020개 중 초기 20,000개를 한 응답으로 로드한 조건이며 응답 지연은 200ms.

## 핵심 결과

각 행은 해당 실험의 중앙값입니다. 단계별로 기준을 재측정했으므로 서로 다른 행을 연속 개선율로 합산하지 않습니다.

| 실험          | 지표                       | 적용 전 | 적용 후 |
| ------------- | -------------------------- | ------: | ------: |
| 포맷터 재사용 | 전체 소요 시간             | 94.38초 | 65.75초 |
| 메시지 memo   | 전체 소요 시간             | 62.06초 | 51.43초 |
| 메시지 memo   | 50ms 초과 작업 총시간      | 17.99초 |  2.08초 |
| 가상화        | 종료 시 DOM 메시지         | 2,000개 |    35개 |
| 가상화        | 콘텐츠 누락 표시 프레임    |    13개 |     2개 |
| 가상화        | 50ms 초과 메인 스레드 작업 |    42개 |     1개 |

초기 포맷터 비교는 당시 문서 기록이며 원본 trace가 삭제됐습니다. 가상화의 콘텐츠 누락 표시 프레임은 layer tree·source·sequence로 중복 제거한 값입니다. 프레임 수를 FPS나 빈 화면 지속시간으로 해석하지 않습니다. 고정 이미지·합성 입력 기준이며 실기기 검증은 별도입니다.

20,000개 검증에서도 종료 시 DOM 메시지는 35개였습니다. 콘텐츠 누락 표시 프레임은 중앙값 3개·최악 10개, 최대 메인 스레드 작업은 중앙값 275.8ms·최악 283.8ms였습니다. 이전 20개 응답 완료→DOM 반영은 중앙값 51.3ms·최악 60.7ms였고, 읽던 메시지 위치 변화는 모두 0px였습니다.

목 API에서 한글 입력·삭제·조합, 전송 후 내역 재조회 방지, 점진 응답, 상품 가로 스와이프와 검색 대상 이동·앞뒤 조회도 확인했습니다. 실제 OS 입력기·모바일 기기·운영 API는 미검증이며, 긴 작업과 일부 콘텐츠 누락이 남습니다. 실제 AI 응답 시간이나 모든 상황의 끊김 해소를 보장하는 결과는 아닙니다.

상품 표시·스와이프 시간 집계를 보완한 뒤 같은 20,000개·CPU 4배 조건에서 예행 1회와 본 측정 5회를 다시 실행했습니다.

| 재측정 지표                              |    중앙값 |    최악값 |
| ---------------------------------------- | --------: | --------: |
| 전송 → 최신 AI 상품 카드 2개 DOM 표시    | 1,178.5ms | 1,278.1ms |
| 완료 허용 요청 직전 → 상품 카드 DOM 표시 |   640.5ms |   666.0ms |
| 이미지 로드 전 가로 스와이프 관측 구간   |   908.1ms |   910.1ms |
| 이미지 decode 후 가로 스와이프 관측 구간 |   886.0ms |   900.4ms |

상품 표시는 최신 AI 메시지 안의 기대한 카드 2개가 DOM에 표시되는 시각이며 이미지 decode·페인트 완료는 제외합니다. 상품이 없는 응답은 시각을 기록하지 않는 회귀 검증을 통과했습니다. 전송→상품 시간에는 목 스트림 완료 허용까지의 대기가 포함되며 실제 AI 지연이 아닙니다. 스와이프 관측 구간은 합성 제스처·300ms 정착 대기·위치 조회를 포함하고 trace 읽기·압축·저장은 제외합니다. 새 스와이프 5회에서도 세로 위치 변화는 모두 0px였습니다. 두 지표는 정의를 바로잡아 다시 측정한 것이므로 이전 값과 개선율로 비교하지 않습니다.

상세 실험 기록, 노션용 문서·이미지와 원본 trace는 저장소 밖에 보관합니다. 벤치마크 코드는 `tests/performance/`에 유지합니다.

## 재현

[브라우저 테스트 실행 환경](../testing.md)을 준비하고 3100·3101 포트를 비운 뒤 실행합니다. 새 결과는 Git 제외 경로인 `performance-results/`에 생성됩니다.

```sh
pnpm bench:chat chat-scroll.spec.ts
BENCH_SCROLL_DOWN=1 pnpm bench:chat chat-scroll.spec.ts
BENCH_PREPEND=1 pnpm bench:chat chat-scroll.spec.ts
BENCH_20K=1 BENCH_SCROLL_DOWN=1 BENCH_LABEL=runtime-218-loaded-20k pnpm bench:chat chat-scroll.spec.ts
BENCH_20K=1 BENCH_PREPEND=1 BENCH_LABEL=runtime-218-prepend-20k pnpm bench:chat chat-scroll.spec.ts
```

상품·스와이프 재측정은 `pnpm bench:chat chat-runtime.spec.ts chat-runtime-extra.spec.ts`로 실행합니다. 이 두 시나리오는 `BENCH_OUTPUT_DIR`에 저장소 밖의 절대 경로를 지정하면 결과와 trace를 그곳에 직접 저장합니다.
