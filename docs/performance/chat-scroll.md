# 채팅 스크롤: 포맷터 재사용과 메시지 memo

측정일: 2026-11-08. `formatKoreanDate`와 `formatKoreanTime`이 매 호출마다 생성하던 `Intl.DateTimeFormat`을 모듈 내 상수로 옮겼습니다. 출력 옵션과 호출처는 그대로이며, 메시지 메모이제이션이나 가상화는 적용하지 않았습니다.

## 측정 조건

- 기존 저장 기준 `pagination-cpu4`와 변경 후 `formatter-reuse-cpu4`를 비교했습니다. 각각 예행 1회 후 본 측정 5회입니다.
- 일반 배포용 빌드, Chromium 156.0.8078.4, headless, 390x844, DPR 1, CPU 4배 감속입니다.
- 동일한 메시지 1,000개와 상품 카드 데이터, 최근 20개부터 20개씩 49회 추가 조회, 응답 지연 200ms입니다.
- 페이지마다 아래 400px 후 위 8,000px 입력을 12,000px/s로 보냅니다. 추가 로드 완료를 기다리는 시간까지 측정합니다.
- 시나리오, 브라우저, 데이터 해시, CPU 배율, 입력 조건, 최종 메시지 수, 커서 조회 수의 일치를 검증했습니다. trace 압축은 측정 종료 후 수행합니다.

고정 테스트 데이터의 한 기기에서 순차 측정한 비교입니다. 실제 서버, 상품 이미지, 휴대폰 GPU 비용이나 스트리밍은 포함하지 않습니다.

초기 비교의 원본 trace와 요약 JSON은 일반 E2E의 `test-results/` 초기화로 삭제됐습니다. 위 표는 당시 기록한 수치이며, 아래 memo 비교에서는 기준과 적용 후를 모두 다시 수집했습니다. 성능 결과 경로는 일반 E2E와 분리했습니다.

## 기존 메시지 memo: 기준 재측정과 비교

`UserChatMessage`와 `AIChatMessage`에 이름 있는 함수로 `memo`를 적용했습니다. `ChatRoomScreen`의 `handleRetry`도 `useCallback`으로 유지해 함수 prop 때문에 사용자 메시지의 렌더 생략이 무효화되지 않도록 했습니다. 기본 props 비교를 사용하며 별도 비교 함수는 없습니다. 메시지 객체와 검색 강조어 등 props가 바뀌면 다시 렌더됩니다. 메시지 객체는 기존 Query 페이지에서 참조를 유지하므로 내역 병합 로직은 변경하지 않았습니다.

날짜 포맷터 재사용은 양쪽에 유지했습니다. 일반 배포용 빌드에서 기존과 동일한 CPU 4배, 고정 데이터, 페이지 크기, 응답 지연, 스크롤 입력으로 각각 예행 1회와 본 측정 5회를 실행했습니다. 브라우저 버전과 데이터 해시를 포함한 조건 일치를 검증했습니다.

각 지표의 5회 중앙값입니다.

| 50ms 초과 긴 작업     |   181개 |    25개 |  86.2% |

### React Profiler와 Performance의 역할

[React Profiler](https://react.dev/reference/react/Profiler)는 React 트리의 렌더 시간과 메모이제이션 효과를 조사하는 데 적합합니다. [memo](https://react.dev/reference/react/memo)는 props가 같을 때 부모로 인한 렌더를 건너뛰지만 컴포넌트 자체 상태와 Context 갱신까지 차단하지 않습니다. 실제 스크롤의 긴 작업, 페인트와 프레임 누락은 Chrome Performance로 함께 검증해야 합니다. 이번 정량 비교는 일반 빌드의 Chrome Performance trace이며, 별도의 React Profiler 기록에서 렌더 횟수를 측정한 결과는 아닙니다.

## 로드된 메시지 수와 하향 스크롤

`BENCH_SCROLL_DOWN=1 pnpm bench:chat`으로 최근 메시지 200개, 1,000개, 2,000개를 각각 초기 응답에 넣고 비교했습니다. 일반 배포용 빌드, headless Chromium, 390×844, DPR 1, CPU 4배 감속에서 폰트와 이미지 준비를 기다렸습니다. 하단에서 48,000px 위에 위치한 뒤 36,000px를 12,000px/s로 내렸습니다. 화면을 통과하는 메시지와 상품 데이터는 동일하며, 측정 중 메시지 추가 조회는 없었습니다. 조건별 예행 1회와 본 측정 3회를 실행하고 회차마다 조건 순서를 바꿨습니다.

| 로드된 메시지 | 콘텐츠 누락 표시 프레임 중앙값 (범위) | 표시 프레임 중 누락 비율 중앙값 | 스크롤 중 전체 드롭 중앙값 | 50ms 초과 메인 스레드 작업 중앙값 |
| ------------: | ------------------------------------: | ------------------------------: | -------------------------: | --------------------------------: |
|         200개 |                               1 (1~1) |                            0.6% |                          0 |                                 1 |
|       1,000개 |                              3 (3~37) |                            1.7% |                          0 |                                 1 |
|       2,000개 |                            13 (11~26) |                            7.2% |                          0 |                                42 |

스크롤 상태의 Chrome `PipelineReporter`를 레이어 트리, 프레임 소스, 시퀀스 번호로 묶었습니다. 표시됐지만 `has_missing_content`가 있는 프레임과 드롭으로만 보고된 프레임을 구분했습니다. 2,000개에서는 콘텐츠 누락과 긴 작업의 중앙값이 늘었습니다. 1,000개 조건의 한 회차에서도 누락이 37건 발생해, 증가 폭에는 회차별 변동이 있습니다. 첫 회차의 메인 스레드 trace에서는 메시지 수가 많은 조건에서 Paint와 IntersectionObserver 계산의 기록 시간이 늘었습니다.

원본 trace 9개, `summary.json`, 중복 집계를 제거한 `frame-analysis.json`은 `performance-results/chat-scroll/loaded-down-cpu4/`에 있습니다. 실제 Lift 입력 대신 Chromium 합성 입력과 고정 상품 이미지를 사용했습니다.

## 상품 카드 content-visibility 실험

상품 카드 묶음에 `content-visibility: auto`와 `contain-intrinsic-block-size: auto 400px`를 적용하고, 같은 하향 스크롤 벤치마크를 조건별 3회 다시 실행했습니다. 일반 배포 빌드와 브라우저 버전, CPU 감속, 화면 크기, 입력 거리를 맞췄습니다. 전후는 순차 측정했습니다.

| 2,000개 조건의 지표                |  기존 중앙값 | CSS 적용 중앙값 |
| ---------------------------------- | -----------: | --------------: |
| 콘텐츠 누락 표시 프레임            | 13개 (11~26) |    31개 (22~34) |
| 표시 프레임 중 누락 비율           |         7.2% |           17.3% |
| 래스터 준비가 부족했던 표시 프레임 |          4개 |            26개 |
| 스크롤 중 전체 드롭                |          0개 |             1개 |
| 50ms 초과 메인 스레드 작업         |         42개 |             1개 |

긴 작업은 줄었지만, 빠른 스크롤의 주된 증상인 콘텐츠 누락은 늘어 CSS를 되돌렸습니다. 래스터가 아직 준비되지 않았다는 플래그도 늘었습니다. 화면 밖 작업을 미루는 방식이 이 조건에서 콘텐츠 누락을 해결하지 못했으므로, 다음 비교 후보는 화면 근처 메시지만 DOM에 유지하는 가상화입니다.

실험 원본 trace와 집계는 `performance-results/chat-scroll/loaded-down-content-visibility-cpu4/`에 있습니다. 같은 고정 이미지와 합성 스크롤을 사용했으며, 실제 마우스에서의 체감은 별도 확인이 필요합니다.

## 메시지 가상화

TanStack Virtual의 window virtualizer를 사용해 페이지 스크롤을 유지합니다. 메시지가 80개를 넘으면 화면 근처 행과 위아래 여유 행 16개씩을 마운트합니다. 날짜 구분선과 메시지에 고정 키를 사용하고, 실제 행 높이는 브라우저에서 측정합니다. 이전 내역이 앞에 추가되면 보던 메시지를 기준으로 스크롤을 보정합니다. 추천 상품의 찜·피팅 변경 상태는 채팅 목록에 보관해 카드가 다시 마운트돼도 유지합니다.

기존 벤치마크와 동일한 CPU 4배 감속, 고정 데이터, 36,000px 하향 입력으로 각각 3회 비교했습니다. 가상화 후에는 로드된 메시지 수와 마운트된 메시지 수를 따로 검증합니다. 행 높이 추정과 보정이 있어 같은 하단 기준 거리에서 시작해도 정확히 같은 메시지에서 시작하는 것은 보장되지 않습니다.

| 2,000개 조건의 지표               |    가상화 전 | 가상화 후 |
| --------------------------------- | -----------: | --------: |
| 스크롤 종료 시 DOM 메시지         |      2,000개 |      35개 |
| 콘텐츠 누락 표시 프레임 중앙값    | 13개 (11~26) | 2개 (1~4) |
| 표시 프레임 중 누락 비율 중앙값   |         7.2% |      1.1% |
| 스크롤 중 전체 드롭 중앙값        |          0개 |       0개 |

재실행은 `BENCH_SCROLL_DOWN=1 BENCH_LABEL=loaded-down-virtual-cpu4 pnpm bench:chat`을 사용합니다. 원본 trace와 집계는 `performance-results/chat-scroll/loaded-down-virtual-cpu4/`에 저장했습니다. 로컬 Chromium의 합성 입력 기준이며 실제 Lift나 모바일 브라우저의 수치는 별도 확인이 필요합니다.

### 일반 채팅에서 이전 메시지 20개 추가

메시지 병합을 쿼리 페이지가 바뀔 때만 수행하고, 기존 메시지 객체의 날짜 라벨은 WeakMap으로 재사용합니다. 메시지 ID의 정렬과 중복 처리 순서는 유지합니다.

`BENCH_PREPEND=1 BENCH_LABEL=prepend-after-cpu4 pnpm bench:chat`으로 CPU 4배 감속에서 예행 1회 뒤 조건별 3회를 측정했습니다. 준비용 응답 하나에 내역을 담고, 상단 스크롤로 이전 페이지 20개를 요청합니다. 응답 지연은 200ms로 고정했고, 지표는 브라우저의 응답 완료부터 DOM의 로드 개수 반영까지입니다.

| 누적 메시지 | 개선 전 중앙값 (범위) | 개선 후 중앙값 (범위) |
| ----------: | --------------------: | --------------------: |
|     2,000개 |  43.6ms (35.1~45.3ms) |  42.2ms (40.9~44.2ms) |
|    10,000개 |  62.1ms (60.9~63.0ms) |  51.3ms (48.4~55.3ms) |

10,000개 조건에서는 약 17% 줄었습니다. 2,000개에서는 범위가 겹칩니다. 실제로 여러 페이지를 누적한 쿼리 캐시, 서버 응답 시간, 페인트 완료 시각은 이 측정에서 다루지 않았습니다. 원본 수치는 `performance-results/chat-scroll/prepend-before-cpu4/`와 `prepend-after-cpu4/`의 `summary.json`에 있습니다.

같은 날짜의 이전 페이지를 맨 위에 붙일 때는 첫 날짜 구분선을 가상 행 밖에 둡니다. 날짜 구분선은 추가 전후에 같은 위치에 남기 때문에, 위치 보정은 첫 메시지부터 시작해야 기존 메시지가 화면에 남습니다. 상단에 한 번 도달한 뒤 이전 메시지 20개만 요청되고 기존 첫 메시지가 화면에 유지되는지를 브라우저 회귀 테스트에서 확인합니다.

### 확장 없이 CPU 감속 비교

일반 배포 빌드, 확장 없는 headless Chromium, 네트워크 감속 없음에서 `BENCH_SCROLL_DOWN=1 BENCH_COMPARE_CPU=1 pnpm bench:chat`으로 실행했습니다. 2,000개를 미리 로드하고 같은 하향 입력을 사용했습니다. 조건별 예행 1회와 본 측정 3회를 교차 실행했습니다.

| CPU 조건  | 콘텐츠 누락 표시 프레임 중앙값 (범위) | 스크롤 중 전체 드롭 중앙값 | 50ms 초과 작업 중앙값 |
| --------- | ------------------------------------: | -------------------------: | --------------------: |
| 감속 없음 |                             1개 (1~2) |                        0개 |                   1개 |
| 4배 감속  |                             2개 (2~3) |                        0개 |                   1개 |

원본은 `performance-results/chat-scroll/loaded-down-compare-cpu/`에 저장했습니다. 고정 상품 이미지와 합성 입력을 사용했으므로, 운영 상품 이미지와 실제 휠 입력의 수동 기록을 이 수치와 직접 비교하지 않습니다.
