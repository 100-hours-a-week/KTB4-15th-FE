# 239번 채팅방 상품 이미지 초기 로딩

## 데이터와 조건 고정

- 로그인된 로컬 브라우저에서 239번 방의 `messages?size=20` 응답을 읽기 전용으로 저장했다. DB는 변경하지 않았다.
- 메시지 20개, 상품 30개. 원본과 고정 응답, 메시지 ID 목록, 이미지 SHA-256은 `performance-results/chat-lcp/room239-fixture/`에 저장했다. 채팅 내용과 이미지는 git에 포함하지 않는다.
- 이미지 URL별 현재 최적화된 640px WebP 바이트를 저장하고, 고정 응답에서 로컬 이미지 경로로 치환했다. 총 30개 약 388KB. Next 이미지 처리 경로는 유지한다. 외부 CDN의 지연·이미지 변경은 전후 비교에서 제외한다.
- 테스트 API가 추천 상품을 공통 상품으로 덮어쓰지 않도록 opt-in 설정을 추가했다. 측정 시작 전 API 응답의 메시지 전체가 고정 응답과 정확히 같은지 검사한다. 이 검사 도입 전 회차는 `*-invalid-products`로 분리하고 비교에서 제외했다.
- 일반 `pnpm build` + `pnpm start`, `reactProductionProfiling: false`, 소스맵 비활성화. 390×844, DPR 1, CPU 4배, CDP 네트워크 1.6Mbps/업로드 0.75Mbps/지연 150ms. 확장 프로그램 없는 Chromium, 매 회 새 컨텍스트와 브라우저 캐시 비활성화, 각각 5회.
- 직접 `/chat/239` 진입. 메시지 표시 후 8초 동안 조작 없이 LCP를 관측한다. trace 비활성화. 이미지 최적화 서버 캐시는 공유되므로 서버 콜드 스타트 비교는 아니다.
- API 응답은 실제 내용을 고정해 로컬 테스트 API에서 재생한다. 운영 백엔드 지연을 재현한 측정은 아니며 Lighthouse 감속 시뮬레이션 점수와 직접 비교하지 않는다.

## 변경

상품 이미지 영역을 IntersectionObserver로 확인하고 화면 위아래 200px 범위에 들어왔을 때 Image를 생성한다. 생성한 이미지는 eager로 로딩하고, 각 캐러셀 첫 카드에는 높은 요청 우선순위를 준다. 옆 카드가 실제로 보이거나 가로 스크롤로 들어오면 그 이미지도 로딩된다. 한 번 표시한 이미지는 계속 유지한다.

기존 브라우저 lazy loading이 근처 과거/가로 카드들을 넓게 미리 요청하던 범위를 좁힌다. 이미지 영역의 aspect-ratio와 상품 정보·버튼은 유지하므로 이미지 대기 중 레이아웃 높이는 같다. 화면 밖 카드를 전부 eager로 바꾸거나 상품 이미지를 추가 압축하지 않았다.

실행 명령:

```bash
BENCH_ROOM239=1 BENCH_LABEL=room239-images-before pnpm bench:chat chat-lcp.spec.ts
BENCH_ROOM239=1 BENCH_LABEL=room239-images-after pnpm bench:chat chat-lcp.spec.ts
```

각 명령은 해당 변경 전/후 코드를 체크아웃한 상태에서 실행한다. 로컬 고정 응답과 `public/bench-chat239/` 이미지가 필요하다. 결과 JSON과 회차별 PNG는 같은 label의 `performance-results/chat-lcp/` 하위 폴더에 저장된다.

## 남은 한계

실제 CDN/Next 이미지 최적화 서버의 콜드 지연과 백엔드 응답 시간은 이 고정 재생에서 제외했다. 기존 Lighthouse의 실제 데이터 8.9초 점수와 직접적인 전후 비교가 아니다. 로딩 범위를 좁혔으므로 빠르게 스크롤하면 기존의 넓은 사전 로딩보다 이미지 준비가 늦을 수 있다. 200px 사전 로딩과 실제 화면 진입 테스트를 두었지만 실기기 고속 스크롤 체감은 추가 확인이 필요하다.

## 최초 표시와 하단 이동 실험

같은 239번 방 스냅샷과 일반 빌드 조건으로 각각 5회 측정했다. 기존 이미지 개선을 적용한 상태에서 두 실험을 독립적으로 비교했다. 모든 회차에서 같은 최신 상품 이미지가 LCP였다.

| --------------------------------------- | ---------- | --------------------------------------- |
| 기준선                                  | 3,180ms    | 78ms                                    |
| 가상 범위 계산 전 일반 행 표시          | 3,184ms    | 80ms                                    |

## 현재 CSR의 Chrome Performance trace

`BENCH_ROOM239=1 BENCH_TRACE=1 BENCH_LABEL=room239-csr-trace pnpm bench:chat chat-lcp.spec.ts`로 5회 기록했다. 239번 방의 같은 고정 응답과 이미지, 일반 빌드, CPU 4배 감속과 1.6Mbps 설정을 사용했다. 직전 실험의 피팅 분리는 되돌린 상태다.

| 항목                                   | 5회 중앙값 |
| -------------------------------------- | ---------- |
| FCP                                    | 504ms      |
| 가장 큰 초기 JS 응답 완료              | 2,171ms    |
| 메시지 요청 전 마지막 JS 응답 완료     | 2,407ms    |
| 첫 메시지 API 요청 시작                | 2,511ms    |
| 마지막 JS 응답 완료 → 메시지 요청 시작 | 107ms      |
| 메시지 API 응답 완료                   | 2,812ms    |
| 상품 이미지 요청 시작                  | 2,912ms    |
| LCP                                    | 3,204ms    |
| 메시지 요청 전 메인 스레드 작업 시간   | 430ms      |
| 메시지 요청 전 50ms 이상 작업 수       | 2개        |
| FCP → LCP 구간의 50ms 초과 차단 시간   | 43ms       |

메인 스레드 시간은 해당 renderer의 RunTask 구간 합집합으로 집계했다. 차단 시간은 각 작업의 50ms 초과 부분 중 FCP부터 LCP까지의 합계다. Lighthouse의 TBT와는 관측 구간과 측정 방식이 다르다. 기록 부하가 포함되므로 비기록 실험과 개선 폭을 비교하는 데는 사용하지 않는다.

대표 trace인 4회차에서 약 119KB의 공용 청크 `1-zcfkj2_svyu.js`는 168ms에 요청되어 2,147ms에 응답을 마쳤다. 이어 해당 청크의 EvaluateScript가 약 84ms 걸렸다. 862B의 `2n5481v8f8rj3.js`는 2,223ms에 요청되어 2,379ms에 응답이 끝났고, 메시지 요청은 2,497ms에 microtask에서 시작했다. 마지막 청크는 공통 오류 화면 코드다. 도착 순서만으로 해당 청크가 메시지 요청을 막았다고 확정할 수 없다.

소스에서 최초 조회는 ChatRoomScreen의 useChatRoomHistory → useInfiniteQuery → getChatRoom 경로다. 이 환경에서 큰 공용 JS가 준비되는 시점과 메시지 요청 사이의 직렬 경로가 길다. 메인 스레드가 비어 있는 시간을 전부 다운로드에 귀속할 수는 없고, 소스맵 없이 React 내부 실행을 개별 앱 함수에 귀속하지 않았다.

원본은 `performance-results/chat-lcp/room239-csr-trace/`의 `run-1.trace.json`부터 `run-5.trace.json`까지다. `results.json`과 `analysis.json`에 타이밍과 집계를 저장했다. 앱 구현은 이번 분석에서 변경하지 않았다.

## CSR 메시지 요청을 브라우저에서 먼저 시작

일반 채팅방의 프로덕션 HTML에 최근 20개 API의 `rel="preload" as="fetch"`를 추가했다. API 클라이언트와 같은 쿠키 전송 설정을 사용한다. 메시지는 기존 클라이언트 쿼리가 받아서 표시한다. 검색 메시지 주변 조회에는 이 링크를 넣지 않는다.

`BENCH_ROOM239=1 BENCH_LABEL=room239-browser-preload pnpm bench:chat chat-lcp.spec.ts`로 일반 빌드에서 5회 측정했다. 기준선은 같은 239번 방 스냅샷, 화면, CPU, 네트워크 조건의 `room239-initial-flow-before`다. 두 측정 모두 trace 기록을 끈 상태다.

| 항목                 | 기준선 중앙값 | 브라우저 선요청 중앙값 |
| -------------------- | ------------- | ---------------------- |
| FCP                  | 500ms         | 564ms                  |
| 메시지 요청 시작     | 2,507ms       | 175ms                  |
| 메시지 응답 완료     | 2,810ms       | 687ms                  |
| LCP 이미지 요청 시작 | 2,890ms       | 2,675ms                |
| LCP                  | 3,180ms       | 2,908ms                |

선요청 후 LCP는 4,200ms, 2,992ms, 2,908ms, 2,904ms, 2,892ms였다. 중앙값은 272ms(8.6%) 줄었지만 첫 회는 기준선의 첫 회인 3,364ms보다 느렸다. FCP 중앙값은 64ms 늘었다. 메시지가 일찍 준비돼도 화면을 그리는 시점은 클라이언트 JS에 의존한다.

모든 회차에서 같은 상품 이미지가 LCP였고, 브라우저 Resource Timing에는 메시지 API 요청이 회차당 한 건씩 기록됐다. 선요청 후에는 initiator가 모두 `link`였다. 테스트 서버에서 측정 중 확인한 요청 수도 스냅샷 검증 1건과 완료된 브라우저 진입 수에 일치했다. 외부 이미지 서버와 운영 API 조건은 별도 검증이 필요하다. 원본은 `performance-results/chat-lcp/room239-browser-preload/results.json`에 있다.

## 알림 SSE 복원 후 현재 CSR Performance

알림의 `void connect()`를 복원하고 239번 방의 같은 고정 메시지 20개와 이미지로 5회 기록했다. 일반 프로덕션 빌드이며 CPU 4배, CDP 지연 150ms/다운로드 1.6Mbps, 390×844/DPR 1, 새 컨텍스트와 브라우저 캐시 비활성화 조건이다. 현재 브라우저 메시지 preload와 초기 위치 확정 후 목록 표시가 적용돼 있다.

실행 명령은 `BENCH_ROOM239=1 BENCH_TRACE=1 BENCH_EXPECT_NOTIFICATION_SSE=1 BENCH_LABEL=room239-sse-on-current-trace pnpm bench:chat chat-lcp.spec.ts`다. 각 회차에서 알림의 connected 이벤트와 SSE HTTP 200 응답, 기록 종료까지 연결이 열린 상태를 검사했다. 연결 종료를 기다리지 않고 메시지 표시 후 8초에 기록을 마쳤다.

5회 모두 같은 최신 상품 이미지가 LCP였고, 메시지 요청은 preload link에서 시작했다. 초기 JS 전송 합계는 316,869B다. 첫 회 LCP는 3,248ms이고 모든 회차를 포함했다.

### 현재 병목

메시지 데이터가 약 0.68초에 준비되지만 메시지/상품 이미지 출력은 초기 JS 준비 이후에 진행된다. 메시지 응답 완료부터 이미지 요청까지 약 1.99초이며 그 구간의 메인 작업은 약 0.46초다. 초기 JS 다운로드를 기다린 뒤 화면을 초기화하는 경로가 현재 고정 조건에서 가장 큰 지연이다. 메인 스레드가 쉬는 시간을 전부 다운로드 시간으로 귀속하거나 공용 청크 전체를 제거 가능한 코드로 보지는 않았다. 해당 공용 청크에는 React/Next 런타임과 모니터링 코드가 함께 있다.

네트워크 preload 덕분에 이전의 약 2.5초 메시지 요청 지연은 줄어들었지만, 초기 JS가 화면 표시를 결정하는 경로는 남아 있다. 알림 연결은 5회 모두 유지됐고 Performance 기록은 정상적으로 종료됐다.

### Lighthouse와 비교하는 방법

Lighthouse 기본 simulated throttling은 수집한 기록을 기반으로 감속 환경을 추정한다. 이번 기록은 CDP가 CPU와 네트워크를 실제로 감속시킨 관측값이다. LCP 지표의 의미는 같지만 감속 적용 방식과 viewport/cache/연결 설정, trace 오버헤드가 달라 절대값은 일치하지 않는다. SSE를 끈 Lighthouse 중앙값 3.77초와 이번 2.916초를 개선율로 비교하지 않는다.

이후 전후 비교에서는 SSE를 켠 이 Performance 조건을 주 기준으로 사용한다. 원본은 `performance-results/chat-lcp/room239-sse-on-current-trace/results.json`, `analysis.json`, `run-1.trace.json`부터 `run-5.trace.json`까지다. 중앙값 회차는 run-3이며 압축하지 않은 JSON을 DevTools Performance 탭에서 열 수 있다.

고정 재생은 실제 알림 이벤트 트래픽, 외부 이미지 CDN과 운영 API 지연을 포함하지 않는다. 알림 stream은 테스트 서버에서 connected 응답 뒤 열린 상태를 유지한다. 브라우저 스냅샷 해시는 기존 239번 방 fixture와 동일하다. 일반 빌드/측정 5회와 `pnpm check`를 통과했다.
