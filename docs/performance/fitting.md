# 피팅 메인 화면 성능 개선

관련 이슈: [#210](https://github.com/100-hours-a-week/KTB4-15th-FE/issues/210)

## 현재 결론

인증 이미지 BFF와 서버 메모리 캐시 실험은 철회했습니다. 현재 전신 사진은 S3 presigned URL을 `unoptimized`로 직접 표시하며, AI의 WebP 저장 적용은 확인하지 않았습니다. 아래 BFF·캐시 실험과 기본 Next.js 최적화 복원은 과거 기록입니다. 후속 서버 조회 병렬화와 피팅 시작 API·공통 알림 의존성 분리는 유지합니다. 현재 방식의 성능은 아직 재측정하지 않았습니다.

초기 HTML의 사진 URL 제공, 이미지 최적화, import 정리와 사진 처리 코드 지연 로딩을 적용했습니다. 최종 simulated Lighthouse 5회 중앙값은 점수 97, LCP 1.538초이며 초기 LCP 6.085초 대비 약 74.7% 감소했습니다. 기능 검증은 사진 변경과 옷장 이동을 포함합니다.

확인한 사실은 초기 JS 전송량 감소와 LCP 개선입니다. 불필요한 초기 다운로드·작업 감소가 이미지와 필수 자원의 경쟁을 줄였다는 설명은 가설이며, 요청 경쟁의 기여도를 트레이스로 검증하지 않았습니다. import 정리와 동적 로딩의 개별 LCP 효과도 분리 측정하지 않았습니다. FCP·TBT는 최종 단계에서 증가했으며 아래 표에 함께 기록합니다.

첫 사진 변경에는 추가 코드 다운로드가 발생합니다. 검증 API 모듈 로딩 실패는 mutation 오류 경로로 전달되지만, 모달 청크 로딩 실패에 대한 별도 사용자 안내는 검증하지 않았습니다. 느린 네트워크에서 첫 변경, 운영 환경과 이미지 캐시 MISS/HIT 비교는 후속 확인 범위입니다.

## 측정 결과

사용자가 제공한 `/fitting` Lighthouse HTML 보고서를 단계별로 5회씩 분석한 중앙값입니다. 보고서의 원본 S3 객체 경로가 세 단계에서 동일함을 확인했습니다. 서명 쿼리는 문서에 기록하지 않습니다.

| 지표          | 초기값        | URL 조기 제공 | 이미지 최적화·배경 제거 |
| ------------- | ------------- | ------------- | ----------------------- |
| 성능 점수     | 78            | 84            | 86                      |
| FCP           | 1.214초       | 1.062초       | 1.061초                 |
| LCP           | 6.085초       | 4.546초       | 4.227초                 |
| TBT           | 33ms          | 32ms          | 33ms                    |
| CLS           | 0             | 0             | 0                       |
| 이미지 전송량 | 280,906 bytes | 280,906 bytes | 15,806 bytes            |

초기 대비 LCP는 약 1.858초(30.5%), 이미지 전송량은 약 94.4% 감소했습니다. 직전 단계 대비 LCP는 약 0.319초(7.0%) 줄었습니다. 이미지 최적화와 배경 제거가 함께 반영돼 각각의 LCP 효과는 분리할 수 없습니다.

최종 5회 모두 `/_next/image`에서 200 응답, `image/webp`, 요청 너비 640px를 확인했습니다. 이미지 본문은 15,356 bytes이며 응답 헤더를 포함한 전송량은 15,806 bytes입니다. 이미지 요청은 1개입니다. 초기 HTML에서 이미지 발견, 높은 요청 우선순위, lazy loading 해제 항목도 모두 통과했습니다.

## 적용 내용

1. 기존 서버 프로필 조회를 재사용해 첫 HTML에 사진 URL을 포함합니다. Query 초기 데이터로 마운트 직후 중복 조회를 방지하고, 사진 변경 후에는 기존 Query 무효화로 갱신합니다. 인증 오류는 기존 갱신 경로로 처리하며 그 외 서버 프로필 오류는 클라이언트 조회로 재시도합니다.
2. `/fitting` 사진의 passthrough loader와 `unoptimized`를 제거해 Next.js 기본 최적화를 사용합니다. `sizes="320px"`, 기본 품질 75와 WebP를 사용하며 브라우저 픽셀 비율에 따라 변형을 선택합니다. `loading="eager"`, `fetchPriority="high"`를 유지합니다.
3. 장식용 배경 이미지와 blur 스타일을 제거하고 전신 사진 한 장만 표시합니다. 회색 카드 배경과 contain 표시를 유지합니다. 기존의 동일 URL 요청은 재사용됐으므로 이미지 요소 감소 자체를 다운로드 절감으로 계산하지 않습니다.

AI·BE, S3 원본, API 계약은 변경하지 않았습니다. S3 썸네일 생성이나 새 의존성도 도입하지 않았습니다.

## 허용 경로와 캐시

측정에 사용한 개발 S3 버킷의 `/body-images/**`만 허용합니다. 가변 서명 쿼리는 그대로 원본 조회에 전달합니다. hostname 환경변수 분리는 롤백했으며 다른 환경의 버킷은 정확한 도메인을 별도로 허용해야 합니다.

공통 `minimumCacheTTL`은 60초입니다. 29cm 최적화에도 적용되는 최소 TTL이며 상한은 아닙니다. 원본의 Cache-Control이 더 길면 그 값이 적용됩니다. 최적화 캐시는 S3 서명 만료와 연동되지 않고, 이미지 URL에서 별도 사용자 인증을 확인하지 않습니다. 따라서 서명 만료 후 접근 차단이나 사진 삭제 즉시 캐시 제거를 보장하지 않습니다.

서명이 바뀌면 별도 캐시 항목이 됩니다. 첫 요청에는 S3 조회와 변환 비용이 들고, 만료된 서명은 새 원본 조회를 실패시킬 수 있습니다. 제공 보고서만으로 캐시 MISS/HIT 조건을 구분하지 않았으므로 두 조건을 나눠 추가 측정해야 합니다.

## 구현 검증

- `pnpm check`, `pnpm build` 통과
- 배경 제거 후 피팅 E2E 5개 통과: 최초 HTML의 사진 1개, 최적화 URL·srcset·서명 유지·우선순위, 초기 프로필 중복 조회 방지, 허용되지 않은 S3 경로 400, 320/390/1280px 사진 버튼
- E2E 이미지 응답은 고정하며 실제 S3 다운로드는 하지 않습니다. 실제 WebP 전달과 전송량은 제공된 Lighthouse 보고서로 확인했습니다.
- 설치된 최적화 엔진으로 합성 RGBA 이미지의 축소와 투명도 유지도 확인했습니다. 합성 이미지 용량은 사용자 사진의 절감량 근거로 사용하지 않습니다.

## 다음 조사: 초기 JS와 CSS

이미지 최적화 후 `3.html`은 사용하지 않는 JS 약 93KB와 예상 LCP 절감 880ms를 보고합니다. 이는 도구의 추정이며 삭제 가능한 코드나 실제 절감량으로 확정하지 않습니다. 사진 변경·검증·모달 코드와 공통 의존성의 초기 포함 여부를 실제 청크와 연결해 조사합니다.

렌더링을 막는 CSS 4개는 합계 약 22KB입니다. `/fitting`에서 필요 없는 스타일인지 확인한 뒤 변경합니다. CSS 삭제는 아직 적용하지 않았습니다.

보고서는 `throttlingMethod=simulate`입니다. 상단 LCP는 시뮬레이션 결과이므로 세부 관측 시간과 직접 빼서 원인을 계산하지 않습니다. 다음 변경은 별도 커밋으로 분리하고 같은 사진·기기·네트워크·캐시 조건에서 5회 중앙값을 비교합니다.

## 4단계: 피팅 페이지의 직접 import

`/fitting` 페이지가 `features/fitting/index.ts`를 통해 가져오면서, 프로덕션 클라이언트 참조 매니페스트에는 옷장·진행·결과 화면까지 같은 청크 묶음에 포함됐습니다. 페이지에서 전신 사진과 착장 선택 컴포넌트를 직접 import하도록 바꿉니다. 옷장 링크와 prefetch 동작, 사진 변경·검증은 유지합니다.

직전 커밋 `ca18f6d`와 import만 변경한 코드를 같은 로컬 설정으로 각각 프로덕션 빌드해 비교했습니다. 전신 사진 컴포넌트의 매니페스트에 연결된 JS 청크를 중복 없이 합산한 값입니다. React·Next.js 등 공통 의존성도 포함하며 페이지 전체 실제 전송량이나 Lighthouse의 미사용 JS 양과는 다릅니다.

| 항목                      | 이전          | 직접 import   |
| ------------------------- | ------------- | ------------- |
| 연결된 JS 청크            | 11            | 10            |
| 청크 파일 크기 합계       | 450,837 bytes | 415,937 bytes |
| 청크별 gzip 크기 합계     | 138,137 bytes | 128,543 bytes |
| 매니페스트의 피팅 UI 모듈 | 7             | 2             |

gzip 합계는 9,594 bytes(약 6.9%) 줄었습니다. 매니페스트에 남은 피팅 UI는 전신 사진과 착장 선택뿐이며 옷장·진행·결과 화면 참조가 제외됐음을 assert로 확인했습니다. 프로덕션 빌드는 통과했습니다. 실제 네트워크 요청과 prefetch의 영향, LCP 변화는 같은 조건의 Lighthouse 재측정 전까지 확정하지 않습니다.

회귀 검증: 피팅 메인과 채팅→피팅→옷장 이동 E2E 7개가 통과했습니다. 옷장에서 선택 상태의 새로고침 유지와 피팅 후보 추가 실패 후 재시도도 확인했습니다.

## Turbopack 번들 분석

`pnpm exec next experimental-analyze --output`으로 내장 분석기를 실행했습니다. 추가 의존성이나 앱 설정 변경 없이 `.next/diagnostics/analyze`에 탐색용 보고서를 생성했습니다. `pnpm exec next experimental-analyze`로 다시 열 수 있습니다.

UI에서 `/fitting`, Client, JavaScript로 필터링한 전체 경로 모듈은 592개, 비압축 약 1.76MB, 압축 추정 약 701.12KB입니다. 이는 분석기가 표시하는 전체 경로 모듈 크기로, 초기 요청뿐 아니라 지연 로딩·호환성 모듈 등이 포함됩니다. 실제 최초 다운로드량이나 앞서 측정한 전신 사진 컴포넌트 청크 합계 128,543 bytes와 같은 지표가 아닙니다. 모듈별 압축 크기의 합계도 실제 청크 압축 전송량과 다릅니다.

클라이언트 JS 출력에 연결된 모듈 크기를 보면 React DOM production 단일 모듈 약 200.7KB, Zod 모듈 합계 약 105.6KB, Sonner 단일 모듈 약 35.7KB, React Hook Form 단일 모듈 약 30.9KB입니다. 모두 비압축 기준이며 삭제 가능한 양을 의미하지 않습니다. Sentry와 Next.js 공통 런타임도 존재합니다. polyfill-nomodule은 호환성 경로이므로 일반 브라우저의 초기 절감 후보로 합산하지 않습니다.

분석기 module_dependencies 그래프에서 다음 정적 import 경로를 확인했습니다.

- `fitting-outfit-section.tsx → features/profile/index.ts → profile-setup-form.tsx → react-hook-form`
- `fitting-outfit-section.tsx → features/profile/index.ts → account-section.tsx → features/auth/index.ts → signup-form.tsx`

따라서 다음 작은 실험은 착장 선택에서 프로필 Query와 mutation key를 공통 index 대신 해당 모델 파일에서 직접 import하는 것입니다. 로그인·회원가입·프로필 폼이 실제 초기 청크에서 제거되는지 다시 빌드·분석해 검증해야 합니다. 이 분석 시점에는 추가 변경을 적용하지 않았으며, 아래 5단계에서 검증합니다. 옷장 링크와 prefetch를 줄일 근거도 아직 확인하지 않았습니다.

## 5단계: 프로필 Query 직접 import

`fitting-outfit-section.tsx`에서 `features/profile/index.ts` 대신 `model/member-profile-query.ts`와 `model/full-body-image-query.ts`를 직접 import합니다. 공통 index에서 연결되던 프로필 설정·계정·인증 폼 의존성을 피합니다. 사진 표시나 변경 기능, 옷장 이동·선택 흐름은 수정하지 않습니다.

같은 프로덕션 빌드와 전신 사진 컴포넌트 연결 청크 합산 기준으로 비교했습니다.

| 항목             | 페이지 직접 import 후 | 프로필 Query 직접 import 후 |
| ---------------- | --------------------- | --------------------------- |
| 연결된 JS 청크   | 10                    | 9                           |
| 파일 크기 합계   | 415,937 bytes         | 357,838 bytes               |
| 청크별 gzip 합계 | 128,543 bytes         | 109,672 bytes               |

gzip 합계는 추가로 18,871 bytes(14.7%) 줄었습니다. 페이지와 프로필 import 변경 전의 138,137 bytes와 비교하면 총 28,465 bytes(20.6%) 감소입니다. 이는 관련 청크 크기의 비교이며 실제 초기 전송량이나 LCP 개선율을 의미하지 않습니다.

`next experimental-analyze --output`을 다시 실행했고 `/fitting`의 클라이언트 JS 출력에서 React Hook Form, 프로필 설정 폼, 로그인 폼, 회원가입 폼의 모듈이 모두 제외됐음을 assert로 확인했습니다. 프로덕션 빌드는 통과했으며, 아래 최종 재측정에는 후속 동적 로딩도 함께 반영됐습니다.

## 6단계: 사진 검증 API와 처리 모달 지연 로딩

사진 표시, 변경 버튼, 파일 입력과 로컬 파일 검사는 초기 화면에 유지합니다. 첫 클릭의 파일 선택은 동기적으로 실행합니다. 공통 전신 사진 mutation은 파일 선택 후 검증 API 모듈을 동적 import하고, 피팅 화면의 처리 모달은 검증·저장 중에만 마운트하는 `next/dynamic` 컴포넌트로 분리합니다. 저장 후 Query 무효화, 오류 메시지, 처리 중 이탈 경고와 피팅 시작 제한은 유지합니다.

사진 카드 전체를 서버 컴포넌트로 바꾸지 않았으며, 저장 mutation과 사진 선택 hook 전체를 지연 로딩하지는 않습니다. 공통 검증 mutation 변경은 프로필 사진 등록에서도 같은 동적 API 로딩을 사용하게 합니다. 동적 import 실패는 기존 mutation 오류 처리 경로로 전달됩니다.

동일한 전신 사진 컴포넌트 연결 청크 기준으로 비압축 합계는 357,838 → 317,292 bytes, 청크별 gzip 합계는 109,672 → 96,625 bytes로 줄었습니다. gzip 감소는 13,047 bytes(약 11.9%)입니다. 프로덕션 loadable manifest에서 처리 모달의 별도 JS·CSS 청크를 확인했습니다. 이 단계 단독의 실제 초기 전송량과 LCP 효과는 분리 측정하지 않았으며, 아래에서 import 변경과 합친 재측정 결과를 기록합니다. 처음 사진을 선택할 때 추가 코드 다운로드가 발생합니다.

프로덕션 빌드는 통과했습니다. 첫 파일 선택, 처리 모달의 Escape 닫기 방지, 검증·저장·사진 갱신, 로컬 파일 오류 시 검증 API 미호출을 E2E 검증 대상에 추가했습니다.

검증 결과: `pnpm check`, `pnpm build` 통과. 기존 사진·옷장 E2E 7개와 새 사진 변경 E2E 2개가 통과했습니다.

## 동적 로딩 후 재측정

## BFF 적용 후 simulate LCP 차이 조사

사용자가 제공한 `4. 동적 로딩`, `5. bff 적용`의 HTML 보고서 각 5개와 현재 브라우저의 기존 측정 Trace를 분석했습니다. 새로운 Lighthouse 측정이나 접근·캐시 정책 변경은 하지 않았습니다.

| 지표 중앙값                                 | 동적 로딩    | BFF 적용     |
| ------------------------------------------- | ------------ | ------------ |
| simulate 성능 점수                          | 97           | 87           |
| simulate LCP                                | 1.538초      | 4.108초      |
| FCP                                         | 1.388초      | 1.068초      |
| TBT                                         | 172.5ms      | 38ms         |
| 관측 LCP (`observedLargestContentfulPaint`) | 527ms        | 450ms        |

두 묶음 모두 simulate 설정은 RTT 150ms, 처리량 1,638.4Kbps, CPU 4배입니다. 이미지 발견 가능·eager·high 우선순위는 유지됐고 본문 크기도 같습니다. 2회차에서 실제 이미지 요청 소요 시간은 약 196 → 248ms인 반면 `metrics.lcpLoadDuration`은 약 1,368 → 3,693ms입니다. 모델 기반 수치를 실제 다운로드 시간으로 해석하거나 개별 구간을 합쳐 최종 simulate LCP를 재구성하지 않습니다.

관측 기록에는 다음 차이가 있습니다.

- 동적 로딩 1~~5회: 관측 LCP 전 초기 JS 16개 중 다운로드 완료 0개. 2회차 이미지 완료 약 469ms, LCP 527ms, 초기 JS는 약 605~~1,031ms에 완료됩니다.
- BFF 2~~5회: 관측 LCP 전 초기 JS 17개 모두 다운로드 완료, 합계 297,315 bytes. 2회차 JS는 약 89~~141ms에 완료되고 이미지 완료 약 317ms, LCP 352ms입니다. BFF 1회차는 초기 요청 시점이 달라 이 카운트 비교에서 제외합니다.
- `network-server-latency`의 localhost:3000 추정치는 이전 약 168~~170ms, BFF 약 8~~17ms입니다. 요청 종류·비율과 실제 응답 조건이 영향을 줄 수 있으므로 이 값만으로 원인을 특정하지 않습니다. 두 묶음은 BFF 비용만 달라진 통제 실험이 아닙니다.

[Lighthouse LCP 계산 진입점](https://github.com/GoogleChrome/lighthouse/blob/main/core/computed/metrics/lantern-largest-contentful-paint.js)과 [DevTools Lantern LCP](https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/models/trace/lantern/metrics/LargestContentfulPaint.ts), [FCP 기반 그래프 구성](https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/models/trace/lantern/metrics/FirstContentfulPaint.ts)을 확인했습니다. 모델은 관측 LCP 시점을 기준으로 네트워크·CPU 작업을 골라 의존 그래프를 만들며, JS 다운로드·실행이 그 시점 전후 어디에 있는지가 모델에 포함되는 작업을 바꿀 수 있습니다. BFF 이미지 응답을 기다리는 동안 JS가 먼저 끝난 실행에서는 더 많은 JS 작업이 모델에 포함됐을 가능성이 유력합니다. 다만 조사한 upstream 소스와 측정 버전의 완전 일치 및 두 실행의 시뮬레이션 그래프 재현은 확인하지 않았으므로, 이를 2.57초 증가의 확정 원인으로 선언하지 않습니다.

현재 브라우저에서 사용자가 이미 실행한 simulate 기록(23:31)을 로컬 임시 파일로 저장해 확인했습니다. 이미지 요청은 HTML parser의 link preload, high 우선순위이며 실제 요청 전체는 약 271ms입니다. 같은 요청의 Server-Timing은 profile 20.2ms, source 107.2ms, transform 124.3ms, total 251.7ms입니다. 따라서 해당 실행에 실제 4초짜리 BFF 처리가 있었던 것은 아닙니다. Trace는 리소스 본문·소스맵을 포함하지 않고 `/private/tmp/fitting-bff-simulate-trace.json.gz`에만 보관하며 저장소에는 추가하지 않습니다.

별도로 사용자가 실행한 DevTools throttling 보고서는 모바일 에뮬레이션·Slow 4G에서 LCP 1.464초, FCP 1.430초, TBT 28ms, CLS 0입니다. LCP breakdown은 HTML 첫 응답 약 100ms, 요청 시작 지연 약 560ms, 이미지 로딩 약 770ms, 표시 지연 약 40ms입니다. 단일 실행이며 정확한 CPU 보정과 실제 저사양 기기는 검증하지 않았습니다. 모든 제공 보고서에 로딩 시간 초과 경고가 있어 결과가 불완전할 가능성도 남습니다.

현재 증거는 BFF의 매번 조회·변환 비용이 존재함을 보여 주지만 simulate LCP 증가 전체를 그 비용이나 캐시 부재에 돌릴 수 없습니다. 인증을 생략하거나 공개 이미지 캐시로 되돌리지 않습니다. JS 추가 분리·서버 캐시 도입도 이번 조사에서는 보류합니다. 정확한 회귀 판정에는 동일 조건의 이전/BFF 실행 기록과 해당 버전의 Lantern 그래프 대조가 필요합니다. 서버 변환 캐시는 반복 요청의 개선 후보이며 첫 요청과 simulate 차이를 해결한다고 보장하지 않습니다.

## 후속 실험: 첫 HTML의 서버 조회 병렬화

`/fitting`의 프로필 조회를 먼저 시작해 `Promise.allSettled`로 실패를 결과로 받아두고, 현재 피팅 작업 조회를 시작해 먼저 기다립니다. 작업 조회 오류·미확인 작업으로의 이동을 먼저 처리하며 이동할 때는 프로필 완료를 기다리지 않습니다. 일반 진입에서만 이미 시작한 프로필 결과를 기다려 인증 오류를 처리합니다. 프로필의 일반 오류는 초기 데이터 없이 렌더링하는 기존 동작을 유지합니다. 먼저 이동한 뒤 프로필 조회가 실패해도 처리되지 않은 Promise rejection을 남기지 않습니다.

일반 진입에서 두 조회를 순서대로 기다리던 시간을 겹쳐 첫 HTML과 사진 발견 시점을 앞당기는 실험입니다. 진행 중인 작업으로 이동하는 경우에도 프로필 요청 자체는 발생하며 취소하지는 않습니다. 이미지 API의 매 요청 소유자 확인과 캐시 정책은 변경하지 않습니다. 실제 LCP 감소 폭은 재측정하지 않았습니다.

검증 대상: 첫 HTML의 사진 포함·공개 최적화 차단·비로그인 사진 API 차단·진행 중인 작업으로의 이동입니다. 마지막 테스트는 프로필 응답을 명시적으로 보류하고도 이동하는지 확인한 뒤 응답을 해제합니다. 이동 대상 응답을 대체하므로 피팅 작업 상세 화면 자체의 검증은 포함하지 않습니다.

검증 결과: `pnpm check`, 프로덕션 빌드, 격리된 Webpack 서버의 E2E 4개가 모두 통과했습니다.

## 후속 실험: 피팅 시작 API와 공통 알림 의존성 분리

Sentry는 변경하지 않습니다. 피팅 시작 API를 mutation 실행 시 동적 import하도록 변경해 청크 다운로드도 기존 pending·중복 클릭 방지·오류 처리 안에서 수행합니다. 사진 검증 API와 처리 모달은 이미 지연 로딩되고 있어 추가로 분리하지 않습니다.

피팅 시작 API만 동적 import한 첫 빌드는 초기 연결 JS gzip 합계가 292,775 → 292,798 bytes로 줄지 않았습니다. 공통 NotificationProvider가 쿼리 키만 사용하면서 `fitting-query.ts`를 통해 피팅 API·스키마에 연결돼 있었습니다. 키 객체를 `fitting-query-keys.ts`로 이동하고 Provider에서 직접 가져오도록 변경했습니다. 기존 model의 재수출을 유지하므로 키 값·호출부의 공개 계약은 동일합니다. API의 인증 갱신·응답 검증은 그대로 유지합니다.

동일한 프로덕션 빌드 진단 파일(`.next/diagnostics/route-bundle-stats.json`)의 `/fitting` 연결 청크 기준입니다. gzip은 각 파일을 같은 방식으로 압축한 합계이며 실제 브라우저 전송량과 다릅니다.

| 항목             | 변경 전       | 변경 후       |
| ---------------- | ------------- | ------------- |
| 초기 연결 청크   | 18            | 17            |
| 비압축 JS 합계   | 953,891 bytes | 946,548 bytes |
| 청크별 gzip 합계 | 292,775 bytes | 290,564 bytes |

gzip 감소는 2,211 bytes(약 0.76%)로 작습니다. 이 결과만으로 LCP 2.5초 달성이나 큰 성능 개선을 주장하지 않습니다. 첫 피팅 시작 시 추가 청크 다운로드가 발생하며 실패는 기존 mutation 오류 처리로 전달됩니다. 새로운 Lighthouse 측정은 하지 않았습니다.

`pnpm check`, 프로덕션 빌드와 격리된 Webpack 서버의 사진 초기 표시·변경·피팅 이동·지연 로딩 후 피팅 시작 성공·실패 E2E 8개가 통과했습니다. 새 피팅 시작 테스트는 요청 중 버튼 비활성화, 선택 상품 ID 전달, 성공 시 선택 초기화·이동, 실패 시 선택 유지·요청 제한 안내를 검증합니다.

공통 알림 의존성 변경을 확인하기 위해 알림 초기 배지·조회 복구·피팅 성공·실패 SSE의 토스트·결과 이동 E2E 7개도 실행해 통과했습니다.

## 비교 실험: 이미지 BFF 철회

사용자 요청으로 `/bff/me/body-image`, 프로세스 메모리 캐시, 해당 전용 테스트와 직접 Sharp 의존성을 제거했습니다. 전신 사진 컴포넌트는 `unoptimized` 없이 프로필의 presigned URL을 `src`로 전달하며, 기존 개발 S3 `/body-images/**` 허용 목록과 기본 Next.js 이미지 최적화를 복원했습니다. 기존 Next 이미지 디스크 캐시를 삭제하거나 운영 서버를 재시작·배포하지는 않았습니다.

사진 검증·처리 모달 지연 로딩, 피팅 시작 API 지연 로딩, 공통 알림 쿼리 키 분리, 서버 조회 병렬화·프로필 대기 없는 작업 이동은 유지합니다. 원본 서명 만료와 변환 캐시 만료가 별개라는 한계도 그대로 남습니다. 롤백 전 BFF 소스와 전용 테스트는 `/private/tmp/fitting-bff-rollback-backup.tar.gz`에 임시 보관했습니다. AI·BE 변경은 없습니다. 실제 Lighthouse 성능은 복원 후 재측정하지 않았습니다.

복원 검증: 단위 테스트 11개, `pnpm check`, 프로덕션 빌드와 사진 초기 표시·변경·작업 이동·피팅 시작 E2E 7개가 통과했습니다.

## WebP 직접 표시 준비

`/fitting`의 전신 사진은 프로필의 `fullBodyImageUrl`을 `unoptimized`로 직접 표시합니다. 초기 HTML의 이미지 URL, eager·high 우선순위, 조회 병렬화와 API 지연 로딩은 유지합니다. 개발 S3 `/body-images/**`는 Next 이미지 최적화 허용 목록에서 제거했으며 29cm 설정은 유지합니다. 기존 변환 캐시 파일을 삭제한 것은 아닙니다.

AI·BE는 변경하지 않았습니다. 서버가 아직 PNG URL을 반환하면 원본 PNG를 그대로 다운로드하므로 이 상태를 WebP 성능 결과로 해석하면 안 됩니다. 동일 사진으로 만든 실제 표시용 WebP의 S3 presigned URL을 프로필 응답으로 제공한 뒤 프로덕션 빌드에서 비교합니다. E2E의 WebP URL과 대체 이미지 응답은 직접 표시 계약만 검증하며 파일 형식·화질·LCP를 검증하지 않습니다.

사진 표시·피팅 시작 E2E는 실제 AWS 버킷 주소 대신 `images.example.com`을 사용하고 브라우저에서 해당 이미지 요청을 대체합니다. URL의 서명은 가짜 테스트 값이며 외부 S3 요청은 수행하지 않습니다.
