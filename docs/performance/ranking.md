# 랭킹 성능 개선 기록

이 문서는 단계별 측정과 실험 당시의 구현을 보존합니다. 과거 단계의 설명은 현재 정책을 뜻하지 않습니다. 최종 동작은 [랭킹 도메인](../domains/ranking.md), 회귀 검증은 [테스트 문서](../testing.md)를 참고합니다.

## 랭킹 숫자 표시 검증

`NEXT_PUBLIC_API_MOCKING=enabled pnpm dev`로 실행하고 `/ranking`의 찜순·조회순을 확인합니다. 기존 MSW 응답은 백·천·만·억 단위와 경계값을 포함한 13개 상품을 제공합니다. DB를 변경하지 않으며 성능 측정용 데이터가 아닙니다.

`tests/unit/number-format.test.ts`에서 영어 K·M·B 단위, 소수점 버림과 단위 경계를 확인합니다. `1234 → 1K`, `12345 → 12K`, `123456789 → 123M`이며 경계값 `999999`는 `999K`로 표시됩니다. `tests/unit/ranking-mock.test.ts`는 두 탭의 고정 수치, 상품 ID 중복과 순위 연속성을 검증합니다.

## 랭킹 이미지 최적화 검증

랭킹 썸네일은 찜 목록과 같은 Next.js 기본 이미지 최적화를 사용합니다. 프로덕션 실행 후 `/ranking`의 Network에서 썸네일이 원본 URL 대신 `/_next/image`로 요청되는지, 응답이 성공하고 이미지 전송량이 줄었는지 확인합니다. 기존 기준과 같은 상품·Lighthouse 설정으로 5회 측정하며 이미지 최적화 캐시의 최초 생성과 재사용 조건을 기록합니다. 이미지 없음 대체 표시와 이미지 확대도 확인합니다. 이번 단계에서는 `sizes="80px"`와 지연 로딩 정책을 유지합니다.

### 이미지 로더 제거 전후 측정

사용자가 제공한 Lighthouse 13.5.0 모바일 시뮬레이션 리포트 각 5회의 중앙값입니다. 대상은 `http://localhost:3000/ranking`이며 저장소 초기화는 비활성화했습니다.

| 지표          | 초기값           | 이미지 로더 제거 후 |
| ------------- | ---------------- | ------------------- |
| 성능 점수     | 74               | 81                  |
| FCP           | 1.216초          | 1.214초             |
| LCP           | 12.340초         | 5.197초             |
| TBT           | 107ms            | 62ms                |
| CLS           | 0                | 0                   |
| 이미지 전송량 | 16,193,314 bytes | 131,984 bytes       |

두 조건 모두 이미지 요청은 38개입니다. 변경 후 38개 모두 `/_next/image`를 사용하고 HTTP 200으로 응답했습니다. 이미지 전송량은 약 99.2% 감소했습니다. 양쪽 모두 5회 전체에 측정 시간 초과 경고가 있어 수치는 불완전할 수 있으며, 이미지 최적화 서버 캐시의 초기 상태는 확인하지 못했습니다. 이후 단계에서 경고 원인을 별도로 확인합니다.

## 랭킹 최초 데이터 서버 조회 검증

`pnpm exec playwright test tests/e2e/ranking/ranking-ssr.spec.ts`로 최초 HTML의 상품 행 포함 여부, 브라우저의 최초 중복 요청 방지, 조회순 전환 요청과 찜순 복귀를 검증합니다. 고정 API와 이미지 실패 응답을 사용하므로 실제 이미지 성능 측정을 대체하지 않습니다.

프로덕션 실행에서는 로그인 후 직접 `/ranking` 진입·새로고침, 빈 목록, 서버 조회 401의 인증 갱신, 서버 오류 후 클라이언트 재시도, 이미지 확대와 탭 전환을 확인합니다. 기존과 동일한 Lighthouse 설정으로 측정하고 서버 조회에 따른 문서 응답 시간 변화와 LCP를 함께 기록합니다. 시간 초과 경고는 계속 별도 확인 대상입니다.

### Next.js 공통 데이터 캐시 검증

랭킹 E2E는 다른 세션의 요청도 캐시된 목록을 받고 백엔드 랭킹 호출이 추가되지 않으면서 회원 인증 호출은 수행되는지 확인합니다. 목 인증은 쿠키의 유효성을 검사하지 않으므로 실제 세션 만료 검증을 대체하지 않습니다. 프로덕션 실행에서 최초 캐시 미스·두 번째 요청 재사용·300초 경과 후 기존 결과 제공 및 백그라운드 재검증을 구분합니다. 캐시 실패·서버 재시작·여러 인스턴스와 실제 인증 실패는 별도 검증 대상입니다. 성능 측정 시 캐시 최초 생성과 재사용을 구분합니다. 이미지 preload와 조회순 클라이언트 조회는 이번 캐시 변경에 포함하지 않습니다.

### SSR과 Next.js 데이터 캐시 비교

사용자 제공 리포트 `3. 서버에서 생성`과 `4. SSR + Next 캐시` 각 5회 중앙값을 비교했습니다.

| 지표           | SSR     | SSR + Next 데이터 캐시 |
| -------------- | ------- | ---------------------- |
| 성능 점수      | 84      | 84                     |
| FCP            | 1.362초 | 1.362초                |
| LCP            | 4.547초 | 4.539초                |
| TBT            | 34ms    | 33ms                   |
| CLS            | 0       | 0                      |
| 문서 응답 시간 | 84ms    | 61ms                   |

화면 성능의 뚜렷한 개선은 확인되지 않았습니다. 두 조건 모두 이미지 38개와 131,984 bytes 전송량은 동일하며 브라우저 랭킹 API 요청은 없습니다. 서버 내부의 캐시 적중·API 호출 감소는 Lighthouse 네트워크 기록으로 확정할 수 없습니다.

#### 시간 초과 원인 조사

캐시 단계의 `1.html`에서 알림 SSE(`/api/v1/notifications/stream`, HTTP 200, `text/event-stream`)가 `finished: false`로 남아 있었습니다. 장기 연결이 시간 초과의 유력 후보지만, 인과관계는 아직 확정하지 않았습니다.

검증 시 브라우저 DevTools의 Network request blocking에서 알림 스트림 URL만 차단한 진단용 측정을 별도로 실행합니다. 실제 서비스의 알림 기능은 제거하지 않습니다. 경고가 사라지는지 확인하고, 차단 시 재연결 요청이나 오류 처리의 영향도 확인합니다. 차단한 결과를 기존 무차단 결과와 같은 조건으로 취급하지 않습니다. 비교 실험은 기준·변경 버전 모두 같은 차단 정책으로 다시 측정해야 합니다.

#### 페이지 전체 ISR 전환 조건

현재 `(service)/layout.tsx`는 회원 조회를 위해 쿠키를 읽고 `/ranking`의 서버 API도 사용자 쿠키를 사용합니다. 따라서 페이지에 `revalidate`만 추가해서는 인증된 페이지 전체가 정적 ISR로 전환되지 않습니다.

페이지 전체 ISR 비교 실험에는 요청마다 실행되는 별도 인증 경계(예: Proxy에서 검증)와, 사용자 요청 쿠키에 의존하지 않고 랭킹을 생성·재생성할 서버용 데이터 조회 경로가 필요합니다. 현재 백엔드의 랭킹은 인증을 요구하고 서버용 조회 경로는 확인되지 않았습니다. 인증 검사를 제거하거나 개인의 로그인 쿠키를 고정해 정적 페이지를 생성하는 방식은 사용하지 않습니다. 이 조건을 해결하기 전에는 기존 SSR + 데이터 캐시를 유지하고 페이지 ISR로 명명하지 않습니다.

### 페이지 전체 ISR 빌드 실험 결과

`/ranking`에 임시로 `revalidate = 300`과 `dynamic = "error"`를 지정해 정적 생성 가능 여부를 빌드로 검증했습니다. 컴파일·타입 검사는 통과했지만 prerender 단계에서 다음 오류로 실패했습니다.

```text
Route /ranking with `dynamic = "error"` couldn't be rendered statically because it used `cookies()`.
```

임시 설정은 제거하고 기존 SSR + 데이터 캐시 구현으로 복구했습니다. `force-static`으로 쿠키를 비우거나 인증 검사를 삭제하는 방식은 적용하지 않았습니다. 현재 API·인증 구조를 유지한 페이지 전체 ISR 전환은 완료되지 않았으며, 이 상태를 ISR 성능 비교 대상으로 측정하지 않습니다.

### 첫 랭킹 이미지 preload

이미지 URL이 있는 첫 상품 한 개에만 preload를 적용합니다. 상품 이미지가 없는 행은 건너뛰고 나머지 이미지는 기존 lazy loading을 유지합니다. SSE를 끈 진단 기준(5회 중앙값: 점수 84, LCP 4.558초, FCP 1.367초, TBT 38ms, CLS 0)과 같은 조건으로 재측정합니다. LCP request discovery의 lazy loading 경고와 preload 링크가 개선됐는지 확인합니다.

첫 이미지 preload에 `fetchPriority="high"`를 함께 전달합니다. 설치된 Next.js 구현이 이 값을 이미지와 preload 링크 모두에 전달하는 것을 확인했으며, E2E에서 최초 HTML의 링크·이미지에 높은 우선순위가 지정되고 나머지 이미지에는 지정되지 않는지 검증합니다. Lighthouse에서 실제 경고 해소와 LCP 변화는 재측정합니다.

### 랭킹 확대창 지연 로딩

랭킹 E2E는 초기 확대창 없음, 클릭 시 확대 이미지 표시, 닫기 버튼, 재열기와 Escape 닫기를 확인합니다. 확대창은 동적 import하고 열 때만 렌더링합니다. 실제 TBT 감소는 동일한 CPU 조건의 Lighthouse 재측정으로 확인해야 합니다. 이전 측정의 기기 성능 지표 중앙값은 preload 단계 3,856.5와 우선 로딩 단계 876으로 달라 하이드레이션 변경의 효과로 단정할 수 없습니다.

### 랭킹 행과 액션 경계 분리

초기 찜순 행은 서버에서 생성해 전달하고 이미지·구매 링크의 인터랙션만 클라이언트 컴포넌트로 분리합니다. 조회순 전환·찜순 복귀와 재조회 시 서버 행이 중복되거나 오래된 행을 고정해서 보여주지 않는지 확인합니다. 기존 preload·높은 우선순위, 이미지 대체 표시와 확대창 동작을 유지합니다.

동적 로딩 전후(7·8단계) 5회 중앙값은 성능 점수 88→91, LCP 1.684초→1.684초, TBT 429→359.5ms입니다. JS 전송량은 402,233→403,624 bytes로 줄지 않았습니다. 동적 import만으로 초기 JS와 하이드레이션 비용 감소가 보장되는 것은 아니며, 이번 서버 행 분리 효과는 다시 측정합니다.

### 랭킹 20개씩 점진 표시

SSR은 첫 20개 행만 생성합니다. API 응답과 초기 쿼리 데이터는 최대 100개를 유지합니다. E2E에서 55개 조회순 응답으로 20→40→55 표시, 순위 연속성, 끝에서 버튼 제거, 추가 표시 시 API 재호출 없음, 탭 복귀 시 20개 초기화를 확인합니다. 실제 100개 찜순 데이터로 최초 HTML에 20개만 포함되는지와 LCP·TBT 변화를 동일 조건에서 비교합니다.

## 성능 측정 종료 후 알림 복구

측정용 SSE 비활성화를 복구하고 알림 연결을 다시 시작합니다. 이후 진단 측정은 코드 변경 대신 요청 차단 조건을 명시해 수행합니다.

### 공통 진입점의 직접 import 검증

서비스 레이아웃·셸에서 인증 가드와 알림 Provider만 직접 import하도록 변경합니다. `pnpm check`, 프로덕션 빌드, 로그인·세션 처리·알림·랭킹 관련 E2E로 동작을 확인합니다. 빌드의 `.next/diagnostics/route-bundle-stats.json`에서 `/ranking`의 초기 JS 크기를 비교하며, 실제 개선은 동일한 SSE·모바일 CPU 조건으로 Lighthouse를 재측정합니다. 번들 크기 감소 비율을 TBT 감소 비율로 간주하지 않습니다.

## 공통 import 변경의 번들 비교

서비스 레이아웃의 인증 가드와 셸의 알림 Provider를 도메인 index 대신 구현 파일에서 직접 import하는 실험입니다. 랭킹 초기 JS에서 로그인·회원가입·프로필 설정·알림 목록·피팅 화면 코드가 제거됐습니다.

| 지표                  | 변경 전         | 변경 후         |
| --------------------- | --------------- | --------------- |
| 초기 JS 비압축        | 1,385,775 bytes | 1,226,560 bytes |
| 청크별 gzip 추정 합계 | 397,643 bytes   | 347,586 bytes   |
| 초기 청크 수          | 20              | 17              |

gzip 값은 로컬 압축 추정치이며 실제 전송량과 다릅니다. 이전 검증에서 빌드 및 랭킹·세션 E2E 7개가 통과했습니다.

### CPU 설정 변경 후 재측정

사용자 제공 `12. 설정 바꾸고 재측정`의 Lighthouse 리포트 5회 중앙값은 성능 점수 91, FCP 1.536초, LCP 1.686초, TBT 342.6ms, 문서 응답 시간 67ms입니다. JS 전송량은 각 352,637 bytes입니다. 5회 모두 시간 초과 경고가 있고 기기 성능 지표는 496.5~933으로 변동합니다. 이전 20개 점진 표시 단계의 중앙값은 점수 93, LCP 1.686초, TBT 294.5ms이므로, 번들 감소를 TBT 개선으로 단정하지 않습니다.

동일 폴더의 최종 `performance2`는 CPU 4.15배·Fast 4G에서 탐색 이후 약 9.41초를 기록했습니다. FCP·LCP는 약 853ms이며 50ms를 넘는 메인 스레드 작업은 약 85ms짜리 하나입니다. 해당 작업은 Next.js 부팅 시 모듈 초기화와 JS 컴파일이며, CPU 샘플의 주요 경로는 hydration 관련 모듈 로딩 약 37ms, 클라이언트 instrumentation 로딩 약 23ms입니다. 후자에는 Sentry 모듈과 초기화가 포함되지만 Sentry 단독 실행 시간으로 해석하지 않습니다. 프레임워크 모듈 준비 시간도 실제 랭킹 행 hydration 시간과 구분합니다.

Performance의 실제 기록과 Lighthouse의 시뮬레이션 TBT는 직접 비교하지 않습니다. 서버 데이터 캐시 적중 여부와 Lighthouse TBT의 원인별 기여도는 미확인입니다. Sentry 제외는 별도 비교 실험 대상으로만 검토하며 운영의 초기 오류 수집 정책은 변경하지 않습니다.

## Sentry 클라이언트 제외 비교 실험

종료된 임시 실험 기록입니다. `instrumentation-client.ts`의 Sentry import·초기화와 전역·서비스 오류 화면의 Sentry import·수집 호출만 제외합니다. MSW 개발 초기화, 오류 화면과 재시도 UI, 서버 Sentry 및 Next.js 빌드 통합은 유지합니다. 이 상태에서는 브라우저 오류 수집이 중단되므로 배포하지 않습니다.

| 지표                  | 기준            | 클라이언트 Sentry 제외 |
| --------------------- | --------------- | ---------------------- |
| 초기 JS 비압축        | 1,226,560 bytes | 1,042,590 bytes        |

초기 청크에서 `sentry.javascript`와 `Sentry.init` 문자열이 없는 것을 확인했습니다. 문자열 검사는 모든 모니터링 코드의 부재를 증명하지는 않습니다. gzip은 로컬 압축 추정치이며 실제 전송량이 아닙니다. `pnpm check`와 프로덕션 빌드는 통과했습니다. 실제 TBT 개선 여부는 재빌드된 서버를 재시작한 뒤 동일한 CPU·네트워크·DSN·캐시·SSE 조건의 Lighthouse 5회 중앙값으로 비교합니다. Performance 기록은 원인 분석용으로 별도 사용합니다.

브라우저 Sentry 초기화와 전역·서비스 오류 수집은 기준 커밋 `40e076e`의 코드로 복구했습니다. Zod import 변경과 실험 기록은 유지합니다.

## Zod import 형태 비교

공통 API·검증 청크 `04oqza_i8g236.js`에는 Zod의 JSON Schema 변환 등 사용하지 않는 코드가 포함돼 있었습니다. 소스에서 Zod를 가져오는 14곳을 `import { z } from "zod"`에서 `import * as z from "zod"`로 바꿔, 번들러가 직접 사용한 export를 식별하도록 했습니다. 스키마 정의, 응답 검증, 타입 추론과 실패 처리는 변경하지 않습니다. 이 효과는 현재 Next.js/Turbopack 및 Zod 버전의 빌드 결과이며 모든 번들러에서 보장되는 것은 아닙니다.

Sentry 클라이언트 제외 상태를 유지한 비교에서 랭킹 초기 JS는 비압축 1,042,590→757,551 bytes, 청크별 gzip 추정 합계 286,284→226,739 bytes로 줄었습니다. 초기 청크 수는 16개로 같습니다. Zod를 포함하는 공통 청크는 약 400KB에서 142KB로 줄었으며 일부 JSON Schema 관련 코드는 여전히 남습니다. Zod Mini 전환이나 응답 검증 제거는 하지 않았습니다. 실제 전송량과 TBT 개선은 이 빌드로 재시작한 서버에서 별도 측정합니다.

### Zod 변경 후 사용자 재측정

`14. zod`의 Lighthouse 6회 전체 중앙값은 점수 97, TBT 185.4ms, LCP 1.687초이며 JS 전송량은 각 230,225 bytes입니다. Sentry 제외만 적용한 이전 5회 중앙값은 점수 95, TBT 238ms, LCP 1.686초, JS 전송량 290,830 bytes입니다. 기기 성능 지표 중앙값은 893.5→886.25로 비슷하지만, 새 측정 2회에서 TBT 321ms·340ms가 발생했고 전체 시간 초과 경고는 유지됐습니다. Zod 변경의 개선 신호는 있으나 간헐적 지연 원인은 미확인입니다.

Performance 기록은 탐색 후 6.21초·9.65초이며 50ms 초과 작업은 각각 58.1ms·57.5ms 하나였습니다. Lighthouse 시뮬레이션 TBT와 직접 동일시하지 않습니다. 다음 비교는 Zod 변경을 유지하고 Sentry만 복구한 프로덕션 빌드로 수행합니다.

### Sentry 복구 후 재측정

`15. Sentry 추가`의 5회 중앙값은 점수 96, TBT 199.5ms, LCP 1.687초이며 JS 전송량은 각 292,031 bytes입니다. 1회차는 기기 성능 지표 3,799.5로 다른 4회(881~905)와 크게 달랐습니다. 해당 회차를 제외한 4회 중앙값도 점수 96, TBT 200.75ms로 비슷합니다. 전체 시간 초과 경고는 유지됐습니다.

Sentry를 복구한 빌드의 랭킹 초기 JS는 비압축 941,523 bytes, 청크별 gzip 추정 합계 288,039 bytes이며 초기 청크는 17개입니다. Sentry 원래 코드와 응답 검증을 유지하면서 Zod import 변경만 적용합니다. 변경 전 Sentry 포함 빌드 대비 JS 전송량 감소는 확인됐으나 TBT 감소분 전체는 측정 환경 차이 때문에 코드 효과로 확정하지 않습니다. 이 상태에서 `pnpm check`, 프로덕션 빌드와 랭킹·세션 E2E 7개가 통과했습니다.

## 공통 링크 prefetch 제외 비교 실험

Zod import 변경과 Sentry 복구 상태를 기준으로 하단 메뉴 5개와 헤더 알림 링크의 `prefetch`만 `false`로 지정합니다. 초기 화면에서 다른 서비스 화면의 RSC 사전 요청 11개가 확인돼, 해당 요청과 후속 처리를 줄일 수 있는지 비교합니다. 실제 클릭 시 Next.js 클라이언트 이동은 유지하지만, 첫 이동의 대기 시간이 늘 수 있습니다. 초기 HTML에서 이미 요청되는 통합 CSS를 제거하는 변경은 아닙니다.

스크린샷의 약 394ms 작업은 Next·React·Sentry가 함께 들어 있는 공통 청크에 귀속됩니다. 이것만으로 prefetch나 특정 라이브러리를 원인으로 확정하지 않습니다. 같은 설정으로 Lighthouse 5회 TBT 중앙값·범위와 RSC 요청 수를 비교하고, 차이가 없거나 화면 전환 손해가 크면 이 실험을 원복합니다. Sentry·알림 SSE·인증 및 데이터 검증은 유지합니다.

사용자 재측정에서 큰 효과가 없고 비슷하다는 피드백을 받아 prefetch 제외를 원복했습니다. 원시 리포트가 제공되지 않아 정량 개선 폭은 미확인입니다. 현재 링크는 Next.js 기본 prefetch를 사용하며 이 실험은 운영 정책으로 채택하지 않습니다.

## 최종 측정과 작업 종료

`16. 최종?` Lighthouse 5회에서 점수는 모두 96, TBT는 200·195·212·205·212.5ms(중앙값 205ms), LCP 중앙값은 1.686초입니다. JS 전송량은 각 292,035 bytes이며 기기 성능 지표 중앙값은 904.5입니다. 이전 Sentry 복구 측정의 중앙값 199.5ms와 차이가 작아 성능 퇴보나 안정적인 200ms 이하 달성으로 결론 내리지 않습니다. 5회 모두 시간 초과 경고가 유지됐습니다.

공통 알림에서 피팅 캐시 키만 별도 모듈로 분리하는 실험도 수행했습니다. 초기 JS 비압축 약 7.3KB, gzip 추정 약 1.6KB가 줄었지만 실제 TBT 효과는 확인하지 못했고 사용자 요청으로 원복했습니다. 알림 서버 조회와 PPR은 적용하지 않았습니다.

최종 앱 코드는 Zod namespace import와 기존 Sentry·응답 검증·알림 SSE·기본 prefetch를 유지합니다. 이번 성능 개선 작업은 종료하며, 추후 개선은 새로운 병목 근거가 있을 때 진행합니다.

## ISR 비교 실험

백엔드 내부 랭킹 API와 요청별 Proxy 인증을 분리해 `/ranking` 5분 ISR을 실험했습니다. 목 환경에서 정적 생성·캐시 HIT·요청별 인증 차단을 검증했고, 실제 백엔드 빌드와 사용자 브라우저의 `X-Nextjs-Cache: HIT`도 확인했습니다. 사용자 측정에서 기존 SSR + 데이터 캐시와 속도가 비슷하다는 피드백에 따라 실험을 원복했습니다. 원시 전후 리포트를 통한 정량 개선 폭은 확정하지 않습니다.

최종 구현은 기존 서비스 레이아웃 인증과 SSR + 300초 랭킹 데이터 캐시입니다. Zod import 개선·Sentry·알림 SSE·기본 prefetch는 유지합니다. ISR용 라우트 그룹·Proxy 인증 분리·내부 키 조회·목 테스트 변경은 제거했습니다. 기존 크롤러의 내부 API 인증과 키 설정은 변경하지 않습니다.
