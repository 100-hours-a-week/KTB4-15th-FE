# 랭킹

## 조회와 인증

- `/ranking`은 로그인과 프로필 완료 확인 후 표시합니다. 기본 기준은 찜순(`WISH`)이고 조회순(`CLICK`)으로 전환할 수 있습니다.
- 서버는 최초 찜순 데이터를 조회해 HTML과 초기 쿼리 데이터로 제공합니다. 조회순은 첫 선택 시 브라우저에서 조회합니다.
- 서버 조회 401은 기존 토큰 갱신 경로로 처리합니다. 나머지 서버 조회 실패는 클라이언트 조회·재시도로 복구합니다.

## 데이터 캐시

- 서버는 캐시 조회 전 `members/me`를 `no-store`로 호출해 현재 요청의 인증을 확인합니다.
- 사용자별 필드가 없는 성공한 랭킹 결과만 `unstable_cache`로 300초 재사용합니다. 키는 버전과 API URL(랭킹 기준 포함)이며 쿠키는 키와 결과에 저장하지 않고 실제 API 호출에 전달합니다.
- 기간 경과 후 요청에서 백그라운드 재검증합니다. 실패하면 기존 결과가 더 오래 유지될 수 있습니다.
- 페이지 전체 ISR이 아닌 SSR + Data Cache입니다. ECS별 캐시는 자동 공유되지 않으며 갱신 시점 차이를 허용합니다. 배포·재시작 시 보존 여부는 볼륨 구성에 따라 달라집니다.
- 초기 서버 데이터가 있는 브라우저 쿼리는 30초 동안 최신으로 취급합니다. 조회순 브라우저 호출은 서버 공통 캐시를 사용하지 않습니다.

### `use cache` 대신 `unstable_cache`를 유지하는 이유

현재 목표는 요청별 인증을 유지하면서 사용자와 무관한 랭킹 조회 결과만 공유하는 것입니다. `unstable_cache`는 기존 SSR·캐시 설정을 바꾸지 않고 조회와 스키마 검증을 통과한 결과를 300초 재사용할 수 있어 선택했습니다.

쿠키를 캐시 키에서 제외하는 것은 백엔드 요청에서 쿠키를 생략한다는 뜻이 아닙니다. 캐시 조회 전에는 요청별 인증을 수행하고, 캐시 미스·재검증 시에는 해당 요청에서 읽은 쿠키로 백엔드를 호출합니다. 캐시 키에 쿠키를 넣으면 동일한 공통 랭킹이 사용자·토큰별로 분리돼 재사용 효과가 줄어듭니다. 이 구조는 응답이 모든 사용자에게 동일하다는 전제에서만 유지합니다.

| 항목             | 현재 `unstable_cache`                  | `use cache` 전환                                                                |
| ---------------- | -------------------------------------- | ------------------------------------------------------------------------------- |
| 선언             | 함수 반환 결과를 래퍼로 캐시           | 함수·컴포넌트에 지시문 선언                                                     |
| 키 구성          | 함수·인자와 지정한 keyParts 사용       | 함수 식별자·인자·캡처한 값으로 자동 구성                                        |
| 갱신 정책        | `revalidate: 300`                      | `cacheLife`로 재검증·만료 정책 지정                                             |
| 프로젝트 영향    | 현재 Cache Components 비활성 설정 유지 | `cacheComponents: true` 활성화와 앱의 동적 경계 점검 필요                       |
| 현재 쿠키 의존성 | 요청 쿠키는 조회 인증에만 사용         | 쿠키를 인자나 클로저로 전달하면 키에 포함되므로 공통 조회 인증 구조 재검토 필요 |

Next.js 16 공식 문서는 `unstable_cache`의 후속 API로 `use cache`를 안내합니다. 현재 선택은 `unstable_cache`가 더 빠르거나 새로운 권장 방식이어서가 아니라, 기존 구조에서 필요한 공통 데이터 캐시를 작은 변경으로 구현하기 위한 선택입니다. 향후 Next.js 업그레이드에서는 API 지원 상태를 다시 확인합니다.

`use cache`는 단순한 함수 이름 교체가 아닙니다. 현재처럼 사용자 쿠키로 인증하면서 사용자 간 동일 캐시를 쓰려면, 쿠키에 의존하지 않는 서버용 조회 등 캐시 경계를 먼저 설계해야 합니다. Cache Components 활성화는 다른 페이지의 쿠키·비캐시 조회와 Suspense 경계에도 영향을 줄 수 있어 별도 빌드·인증 회귀 검증 대상으로 다룹니다. `use cache` 전환 자체가 TBT 감소나 ECS 인스턴스 간 캐시 공유를 보장하지는 않습니다.

다른 대안도 현재 요구와 구분합니다.

- `fetch`의 `next.revalidate`: 인증 쿠키를 포함한 요청 옵션이 캐시 키에 영향을 주므로 현재 공통 결과 공유 정책과 다릅니다.
- React `cache()`: 서버 요청 간 300초 저장 대신 같은 렌더링 요청 안의 중복 작업 제거에 사용하는 기능입니다.
- 백엔드 Redis: 실제 도입 범위·TTL·무효화 정책을 확인한 뒤, Next.js 캐시를 유지할 가치와 데이터 지연을 함께 검토합니다. Redis 도입만으로 Next.js 인스턴스별 캐시가 자동 동기화되지는 않습니다.

참고: [unstable_cache](https://nextjs.org/docs/app/api-reference/functions/unstable_cache), [use cache](https://nextjs.org/docs/app/api-reference/directives/use-cache).

## 표시와 점진 렌더링

- 기준별 최대 100개 데이터는 한 번에 받되 최초 HTML에는 12개 행만 포함합니다.
- 목록 끝 200px 이내에서 12개씩 추가 표시하며 추가 API 호출은 없습니다. 수동 `상품 더 보기`도 지원합니다. 다른 탭으로 전환하면 표시 개수를 초기화합니다.
- 가상화가 아니므로 끝까지 스크롤하면 전체 행이 렌더링됩니다.
- 최초 행은 서버에서 구성하고 이미지 확대와 구매 클릭은 클라이언트 액션으로 처리합니다. 재조회 이후에는 최신 쿼리 데이터로 표시합니다.
- 집계는 영어 compact 단위 K·M·B 등을 사용하고 소수점은 버립니다. 예: `1,234 → 1K`, `999,999 → 999K`.

## 이미지와 구매 링크

- 썸네일은 Next.js 기본 이미지 최적화와 `sizes="80px"`를 사용합니다.
- 이미지 URL이 있는 첫 상품 하나에만 preload와 높은 요청 우선순위를 적용하고 나머지는 lazy loading합니다.
- 이미지가 없거나 로딩에 실패하면 상품 종류에 맞는 대체 아이콘을 표시합니다.
- 확대창 코드는 동적으로 가져오며 열 때만 마운트합니다. 확대 이미지는 원본 URL을 사용합니다.
- 구매 링크는 새 탭으로 열고 클릭 집계를 요청합니다.

검증 방법은 [테스트 문서](../testing.md), 측정과 실험 이력은 [성능 개선 기록](../performance/ranking.md)을 참고합니다.
